# Phase 8 — 敵対的QAおよびゲームプレイ信頼性監査 計画

## 背景・目的
Pixel Pilferer は Phase 1 から Phase 7 にわたり、ゲームエンジン、決定論的ルール、レンダラー、ソルバー、20レベル+3デモのキャンペーン、ピクセルアート・音響、UI・進行管理・セーブ永続化を実装してきた。
本フェーズ（Phase 8）では、開発者の自己申告を一切信用せず、懐疑的な独立QAリードの視座から「未検出の欠陥」「境界条件の不整合」「アンドゥ/アニメーション競合」「ファジング耐性」「データ破損・セーブ異常」「ソルバーの最短経路主張の正確性」「パフォーマンス/メモリリーク」を敵対的に検証・監査する。
すべてのP0/P1欠陥を最小限の安全な修正で修復し、回帰テストで証明し、包括的な `docs/QUALITY_AUDIT.md` を作成してリリース判定（GO / NO-GO）を下す。

### 仕様

#### 1. 敵対的ストレステスト仕様 (AUDIT 2 & 3)
- 高速連打・アニメーション割り込み:
  - アニメーション中にリスタート・アンドゥ・移動・インタラクトが連続発生した際、モデル位置とビュー描画が完全に一致すること（デシンクゼロ）。
  - クライアント領域外・負の座標クリック時に例外や不正入力が発生しないこと。
- 10,000手ランダムファジング (Seed固定):
  - 固定シード（例: 42, 1337, 2026）による擬似乱数アクション系列（MOVE, INTERACT, UNDO, RESTART）。
  - 各アクション後に以下を検証:
    1. プレイヤー座標が盤面内かつ非壁・非ブロック床・非空ボイドであること。
    2. 保持ブロック数が 0 または 1 であること。
    3. 全ブロック座標が一意であり、重複・消失・増殖がないこと。
    4. アンドゥスタック整合性（RESTART で初期状態と同一になること）。

#### 2. ソルバー網羅性・最短性検証仕様 (AUDIT 4)
- 全23レベルの初期状態からソルバーを実行し、返された解アクション系列を `BoardModel` で実際に1手ずつ再生。
- 終了時に `model.is_completed()` が真であること。
- ソルバーの重複探索抑止キー `BoardState.get_canonical_key()` の衝突・抜け漏れがないこと。
- 小規模な手計算可能なフィクスチャ（3x3, 4x4）に対する最短手数の厳密検証。

#### 3. セーブデータ耐障害性仕様 (AUDIT 6)
- 存在しないファイル、空ファイル、壊れたJSON（`{ "unclosed: `）、型不一致（`schema_version: "invalid"`）、不正なステージ名（`"ch99_99"`）、範囲外数値（`master_volume: -5.0` または `999.0`）を注入。
- クラッシュせずデフォルト値またはバックアップから復旧し、ゲームが正常起動すること。

#### 4. パフォーマンス＆リーク監査 (AUDIT 8)
- 100回連続のリスタートおよびチャプター間遷移を実行し、メモリ・ObjectDB・RID割り当ての増大をプロファイリング。
- 必要に応じてクリーンアップ処理の補強。

## 実装ステップ

### Phase 1: AUDIT 1 — プロジェクトヘルス＆静的コード監査
1. ディレクトリ構造、Godot設定（`project.godot`）、未使用アセット、重複コードの静的スキャン。
2. 警告、クラス依存関係、循環参照の有無の検証。

### Phase 2: AUDIT 2 — 盤面状態の整合性＆エッジケース破壊テスト
1. アニメーション中のアンドゥ、リスタート、不正操作の連打テストを実装。
2. 盤面外・負の座標クリック時の境界値テストを実装。
3. クリア後の追加入力拒否テストを実装。

### Phase 3: AUDIT 3 — 決定論的ランダムファジングハーネスの構築と実行
1. Python および Godot で固定シード（42, 1337, 2026）による 10,000手ファジングテストを実装。
2. ブロック不変量、位置不変量、整合性の厳密チェックと実行。

### Phase 4: AUDIT 4 — ソルバー厳密性＆最短性検証
1. 全23レベルの解の再検証と安定性テスト。
2. 小規模フィクスチャによるBFS最適性確認。

### Phase 5: AUDIT 5 & 6 — キャンペーン完全性＆セーブ障害耐性
1. 23レベルの進行アンロックチェーンの網羅テスト。
2. 不正JSON、異常値、破損データ復旧テストの実施。

### Phase 6: AUDIT 7, 8, 9 — 描画・パフォーマンス・定性プレイ監査
1. 連続リスタート（100回）でのメモリ・ノード破棄状況の確認。
2. 高コントラスト、色覚記号、UIレイアウトの整合性検証。
3. チュートリアル・難易度・操作フィードバックの定性評価。

### Phase 7: AUDIT 10 — 欠陥のトリアージ・修正・回帰検証
1. 発見された欠陥のP0〜P3分類。
2. 欠陥に対する再現テスト作成と最小限の安全なコード修正。
3. 全テストランナーによる回帰防止確認。

### Phase 8: 最終公式報告書の作成とコミット
1. `docs/QUALITY_AUDIT.md` の作成（テスト結果、監査結果、GO/NO-GO判定）。
2. ローカルGitコミットの作成。
